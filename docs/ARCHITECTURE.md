# Architecture

Le Jardin is a static site with one serverless function. Everything the player does happens in the browser, and the garden is saved in the browser's storage. This page explains how the game runs, where its rules live and how to change one. The table of every file is in the [README](../README.md#architecture).

## How the game runs

1. `index.html` (generated by `npm run generate`) is a small loading shell. Before anything else the browser loads the helpers in `lib/` as plain scripts: the translation runtime, the Living Lesson engine, workshop mode and the five rule modules.
2. After the first paint the shell fetches `game.css` (the styles), `game.logic.js` (the game class), `game.template.js` (the template, made into code) and the game's own runtime, `lib/runtime.js`, with React. All three game files come from the canonical source, `Permaculture Garden v2.dc.html`, which keeps the game in the language of the Claude app's design canvas, where its first version was designed: a template of `{{ values }}`, `<sc-if>` and `<sc-for>` (see below), and a logic class whose `renderVals()` gives the values. The build ships the class as a script of its own, so the browser compiles it while it downloads; the styles of the source's `<helmet>` as a stylesheet of its own, so the browser reads them once; and the template as code ([`scripts/template-compiler.mjs`](../scripts/template-compiler.mjs)): one function for each part of the page, which makes React's elements, so the browser does not read the template as HTML, walk it and compile it at every start, and no code is made from text. Before the game starts, the shell has the cover's typefaces ready ([START-PERFORMANCE.md](START-PERFORMANCE.md)). The runtime gives the class its base, `DCLogic`, draws the template with the values of `renderVals()` and draws again at every `setState()`. A state the game cannot draw (`renderVals()` throws) shows the boot screen's retry card instead of the game until a later change draws it again, and the error is in the console.
3. The game class keeps the state of the garden, draws every screen, plays every sound and saves the game. Whenever a rule has to decide something — what a build costs, whether a crop can be sown now, which act comes next, who comes to live in the garden — it asks a rule module through `this.rules`.

The only server boundary is `api/garden-reflection.js`, the optional Living Lesson; it never decides rules, points or outcomes.

## The template's language

The template is HTML with a few additions, which the build reads ([`scripts/template-compiler.mjs`](../scripts/template-compiler.mjs), pinned by `npm run test:template`). What it does not know stops the build with the source's line to change.

| Write | Means |
| --- | --- |
| `{{ garden.size }}` | A value of `renderVals()`, step by step; a step from nothing gives nothing instead of an error. `==`, `===`, `!=` and `!==` compare two values, a leading `!` turns one round, and `true`, `false`, `null`, numbers and quoted text are themselves. |
| `<p>{{ title }}</p>` | In a text, a value becomes a `<span class="sc-interp">`; null, true and false draw nothing, an element or a list of them draws as it is. A value the logic never gives draws nothing and warns once in the console (the translation checks treat that warning as an error). |
| `title="{{ name }}"`, `title="Go to {{ name }}"` | An attribute that is one whole value keeps it as it is (a function for an event, an object for a style); text around values joins them as text. An attribute that begins with `{{` and ends with `}}` is read as one value, so `{{ a }} {{ b }}` gives nothing: join such values in `renderVals()`. |
| `<sc-if value="{{ open }}">…</sc-if>` | The content while the value is true. |
| `<sc-for list="{{ items }}" as="item">…</sc-for>` | The content once for each item, under the name in `as` (`item` if none); `{{ $index }}` is the item's place. |
| `sc-camel-on-click="{{ onSave }}"` | An attribute name with capitals, which HTML would lower: `sc-camel-on-click` is `onClick`, `sc-camel-view-box` is `viewBox`. `class` is `className` and `for` is `htmlFor`. |
| `style-hover="color:#5E7E4A"` | Styles for `:hover`: the element gets a class and `game.css` the rule. |

## Rules decide, the game speaks

The rules of the game live in five modules:

| Module | In the browser | Decides |
| --- | --- | --- |
| [`lib/economy.js`](../lib/economy.js) | `PermacultureEconomy` | Prices in euros and game shares, reclaimed materials, how a placement is paid, milestones, what a gift changes and that it never pays the giver, which elements are a genuine surplus, stall income, chore rewards, and what the seasons do to the shared pool. |
| [`lib/community-table.js`](../lib/community-table.js) | `PermacultureCommunityTable` | When the community table answers, how likely a neighbour leaves an offer and which one, the table as the seasons turn, and what taking an offer costs the shared pool. |
| [`lib/seasons.js`](../lib/seasons.js) | `PermacultureSeasons` | The order of the seasons, planting windows, sowing from the seed bank, growth and winter, harvest windows and yields, apple trees and their pollination, and what each season leaves to gather. |
| [`lib/acts.js`](../lib/acts.js) | `PermacultureActs` | The six acts of the guided journey, what opens when (the community table, asking the garden, wild neighbours, pests), the unlock cards, the journey's suggestions, the first cycle and a flourishing garden. |
| [`lib/wildlife.js`](../lib/wildlife.js) | `PermacultureWildlife` | What each wild neighbour needs, who arrives and who may visit, how the residents' stories advance, and when a pest breaks out, holds the crops and settles. |

What every rule module promises:

- **Only what it is given.** A rule reads no page, storage, clock or network and draws no random numbers. Where chance plays a part (a neighbour leaves an offer, a visitor comes), the game draws `Math.random()` itself and passes the number in, or compares it with a chance the rule returns.
- **No words.** A rule returns numbers, ids and short codes such as `"seedbank"`, `"low"` or `"closed"`. The game turns them into sentences, because the translation runtime and the translation audit (`scripts/audit-i18n-source-strings.mjs`) read the English text in the canonical source.
- **Tables that cannot change by accident.** Rule tables are frozen.
- **One shape for every helper.** Each module is wrapped like `lib/workshop.js`: a global in the browser, `require()` in Node.

Some tables carry both rules and words: a price and what the element is often made from, a wild neighbour's needs and its name, a story beat's condition and its text. The rule part lives in the module and the words stay in the canonical source under the same ids. The game joins them into the tables it reads (`withRules`, `withRulesByKey`, `storiesWithRules`), so the rest of the game still reads `this.econ`, `this.wildlife` or `this.pestPressures`. Tables that are mostly words stay in the source and are passed to the rules: what neighbours can offer (`giftPool`), the visitor quizzes (`visitDefs`) and where each neighbour spends the winter (`awayWinter`).

The other helpers in `lib/` follow the same idea for their own area: `i18n.js` (translation), `living-lesson.js` (the deterministic Living Lesson engine, shared with the server), `workshop.js` (workshop mode), `offline.js` (playing without a connection, shared with `sw.js`) and `garden-file.js` (the garden saved to a file and loaded back). The last two load only when they are needed, not as `<script defer>` in the page, so the build does not count them among the rules.

## Tests

- `npm test` runs the unit tests of each rule module through `npm run test:rules`: [`scripts/test-economy.mjs`](../scripts/test-economy.mjs), [`test-community-table.mjs`](../scripts/test-community-table.mjs), [`test-seasons.mjs`](../scripts/test-seasons.mjs), [`test-acts.mjs`](../scripts/test-acts.mjs) and [`test-wildlife.mjs`](../scripts/test-wildlife.mjs). They read like the rules: *a greenhouse costs €220, or €130 with an old window and planks*; *a closed rain barrel is not a drinking place for birds*.
- [`scripts/test-rules-words.mjs`](../scripts/test-rules-words.mjs) keeps the two sides in step: the page loads every rule module before the game, every rule has its words and every word its rule, every id a rule names exists in the game, the source keeps no copy of a rule table, and the game gives the same answers as the rules.
- The browser journeys (`npm run test:e2e:core` and the others listed in the README) play the game in Chromium, so they show that the game still asks the rules and shows their answers.

## Changing a rule

**Whoever touches a rule first moves it to `lib/` and tests it.**

1. Find where the game decides it in the canonical source.
2. Move the decision into the module of its area, as a function of what it needs; leave the words in the source. A new area gets a new module, loaded with a `<script src="lib/…">` line before the runtime tag and added to the list in `scripts/test-rules-words.mjs`.
3. Let the game call it, and keep the names of the game's methods: the browser journeys use them.
4. Write the unit test for the behaviour you keep first, then change the rule and its test together, so the change is visible in the test.
5. Run `npm run generate`, `npm test` and `npm run test:e2e:core`.

## Rules still in the canonical source

Move these when you work on them:

- the four resilience values and the garden score (`gardenSystems`, `gardenScore`; tested by `scripts/test-garden-score.mjs`) and the design connections (`guildDefs`, `activeGuilds`, `systemLinks`);
- the seasonal challenges (`gateDefs`, `pickGate`, `applyChallengeImpact`) and their lasting effects;
- the kitchen and the seed bank (recipes, preserving, seed swaps);
- the first-gift hint, the catalogue's "affordable" label, and how a saved game is checked when it loads.
